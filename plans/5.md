# Plan for #5: Enable the metrics endpoint in the deployment

## Goal
Enable the existing plain-text metrics listener in the Kubernetes deployment
and document how to configure and access it. Keep application behavior,
metrics implementation, and HTTP API routes unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **Confirmed — `src/config.ts` (`loadConfig`): no:** already reads
  `METRICS_ENABLED` and requires a valid `METRICS_PORT` when enabled.
- **Confirmed — `src/server.ts` (metrics listener): no:** already serves
  metrics on the configured metrics port and logs its startup.
- **Confirmed — `k8s/configmap.yaml` (yes):** currently disables metrics and
  must set `METRICS_ENABLED: "true"` plus a valid `METRICS_PORT`.
- **Confirmed — `k8s/deployment.yaml` (yes):** currently exposes only the HTTP
  container port; declare the metrics container port for deployment clarity.
- **Confirmed — `README.md` (yes):** environment table exists but needs
  deployment/access instructions for the metrics endpoint.
- **Confirmed — `test/app.test.ts` (no):** configuration validation already
  covers enabling metrics and requiring `METRICS_PORT`; no app route changes.
- **Confirmed — `public/index.html` and `e2e/smoke.spec.ts` (no):** the web
  page does not use the metrics listener.
- **Plausible — `k8s/service.yaml` (no):** may not need a metrics Service
  because the ticket asks to enable the endpoint in the deployment; verify
  whether cluster access is expected through the pod/container port.
- **Open — none.**

## Tests
- No new unit or browser tests expected; existing config tests cover the
  enabled/required metrics settings.
- Run `npm run verify`; inspect manifests and, after push, rely on the
  pipeline rollout/stability checks.

## Environment contract
`METRICS_ENABLED` and `METRICS_PORT` are already declared in `src/config.ts`
and documented in the README. The ConfigMap must provide both values, with
`METRICS_PORT` different from the HTTP `PORT` (use `9100`).

## Risks
- A missing or conflicting metrics port will make the pod exit at startup.
- Exposing the wrong Kubernetes port could make the listener unreachable or
  mislead operators, while rollout and stability gates may fail.
- Pipeline risks include manifest application, rollout, stability, smoke, and
  browser gates; application unit/build gates should remain unchanged.
