# Plan for #2: Reject CO2 values outside 0 to 500 g/km

## Goal
- Enforce validation so API clients cannot submit CO2 values below 0 g/km or above 500 g/km.
- Keep existing valid runs and current validation error format unchanged except for the new range detail.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- Confirmed: `src/runs.ts` — `validateNewRun()` currently checks type and NaN only; this is the exact validation point for the CO2 range rule. change: yes
- Confirmed: `test/app.test.ts` — API tests cover validation and error details; add a specific failing case for out-of-range CO2 values. change: yes
- Confirmed: `public/index.html` — browser form serializes the number and displays `details` when rejected; no direct client-side validation is currently implemented. change: no
- Plausible: `e2e/smoke.spec.ts` — smoke test may hit the form path but does not assert range handling; verify after the API fix. change: no
- Open: none.

## Tests
- `test/app.test.ts`: add assertions that `POST /api/runs` with `co2GramsPerKm: -1` and `501` returns HTTP 400 and includes the range message in `details`.
- Keep the existing invalid-input test covering `vehicleId`, `cycle`, and non-numeric CO2 values.

## Environment contract
- No config or environment variable change required; `src/config.ts` and `k8s/configmap.yaml` are out of scope.

## Risks
- Validation could accidentally reject legitimate values if the range logic is placed in the wrong layer or the test asserts on the wrong message.
- Browser UI still allows typing out-of-range values until the server rejects them, which is acceptable unless product requires client-side blocking.
- Pipeline risk is limited to unit tests and browser smoke verification, not rollout or config drift.
