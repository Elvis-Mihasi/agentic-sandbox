# Plan for #6: Add run status transitions

## Goal
Add `PATCH /api/runs/:id/status` so a run can move from `planned` to
`running`, then from `running` to `done`, returning the updated run. Keep all
existing run creation, listing, retrieval, and web-page behavior unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **Confirmed — `src/runs.ts` (`RunStatus`, `RunStore`): yes:** owns the status
  type and in-memory records; add transition validation and status mutation.
- **Confirmed — `src/app.ts` (API routes/error handler): yes:** add the PATCH
  route, parse/validate the request status, return 404 for unknown IDs and 409
  `{ error: "invalid transition", from, to }` for disallowed transitions.
- **Confirmed — `test/app.test.ts` (`runs api`): yes:** add supertest coverage
  for the happy path, invalid transition, unknown ID, and invalid status input.
- **Confirmed — `README.md` (API table): yes:** document the new endpoint and
  its 404/409 behavior.
- **Confirmed — `public/index.html` and `e2e/smoke.spec.ts` (no):** the issue
  is API-only and the page has no status-transition control.
- **Confirmed — `src/config.ts` and `k8s/configmap.yaml` (no):** no
  environment variables are introduced.
- **Plausible — `package.json` / pipeline (no):** existing TypeScript, Vitest,
  build, and deploy checks should cover the changed API; verify with commands.
- **Open — none.**

## Tests
- `test/app.test.ts`: verify `planned -> running -> done`, reject
  `planned -> done` with 409 and transition fields, return 404 for an unknown
  ID, and reject a missing/invalid status with the repository's JSON error
  shape.
- Run `npm run verify`; no browser test is needed because the web page is
  unchanged.

## Environment contract
No variables are added or changed. `src/config.ts`, `k8s/configmap.yaml`, and
the README environment table remain synchronized.

## Risks
- Transition logic must prevent skipped or reversed states while preserving
  the existing `RunStatus` values.
- Invalid request bodies must not become silent or success-shaped updates.
- Pipeline risks are the lint/unit/build gates plus deploy rollout, stability,
  smoke, and browser gates; the latter should be behaviorally unchanged.

None.
